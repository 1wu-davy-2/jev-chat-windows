# 飞书接入

2026-09-29 排查 + 实测：飞书有没有现成的 jev-chat、要不要给本项目加飞书、怎么加。

## 一句话结论

**Windows 版 jev-chat 目前一个都不支持飞书**（上游 143 个 fork、issue/PR 里 0 条提过飞书）。

但排查里有个反直觉的发现，直接决定后面怎么做：**飞书桌面端不用 OCR**——它的控件树里有正文，
跟微信正好相反。微信那条路之所以是本仓库现在这样（截图 + 一整套阈值），是因为微信界面自绘在
GPU 画布上、控件树是空的（见 `KICKOFF.md`「为什么走 OCR」）。**飞书没这个问题。**

**这条已经在本机真机上验过了**（`probe/probe_feishu.py`，2026-09-29）：飞书开着聊天窗口时，
UIA 能读出 **1767 个节点、388 个 TextControl、36 条消息**，正文、收发方向、消息类型全都在。
详见下面「实测结果」。

## 关键发现：飞书桌面端的控件树里有正文

`iikawa-games/lark-mbti-jev` 的 `feishu_mbti/accessibility.py`，头一行 docstring：

> Read Feishu's desktop text and coordinates through Windows MSAA.
> **No screenshots, OCR, selection changes or client injection are used here.**

具体读法（同一个文件）：

- `chat()` —— 广度优先遍历控件树，找 `accName` 里含 **`messenger-chat:`** 的节点，拿它的
  `accLocation` 当消息区矩形。遍历上限 240 个节点 / 0.75 秒。
- `text()` —— 从 `obj.accName[child_id]` 取文字，`accRole` 在 **40–43**（文本角色）才算，
  单条长度 ≤ 2000 字符。上限 4000 节点 / 2 秒，**读不完就整份丢掉**（不要半份）。
- 技术栈：`comtypes` 调 `oleacc.dll` 的 `AccessibleObjectFromWindow` / `AccessibleChildren`，
  纯 stdlib + comtypes，没有额外依赖。

它顺带处理掉的两件事，本仓库现在是花力气自己做的：

| | 本仓库（微信） | `lark-mbti-jev`（飞书） |
| --- | --- | --- |
| 定位消息区 | `capture.chat_area()` 认底色和细横线，纯像素锚点 | 找 `messenger-chat:` 容器，直接给矩形 |
| 虚拟化列表 | 不需要考虑 | 有专门处理：内容比容器高 = 滚动列表；**滚出视野的消息可能仍留在虚拟树里**，按 `clip` 过滤 |

## 实测结果（2026-09-29，本机真机）

探针 `probe/probe_feishu.py`。**纯读屏，不需要 `lark-cli`，不需要开放平台 API，不需要任何凭证。**

### 先踩的坑：最小化的窗口读不到

飞书窗口最小化时，UIA 只有 **131 个节点**、1 个 TextControl，坐标一片 `-32000`——
全是界面壳子（60 个按钮、19 个页签），**一个正文都没有**。这跟微信那条「窗口不能最小化」
是同一个道理（Windows 不渲染最小化窗口），只是这次的后果落在无障碍树上而不是截图上。
`--unminimize` 走 `SW_SHOWNOACTIVATE` 还原、再压到最底层（跟 `app/capture.py:unminimize()` 同一套，
不抢焦点）。

**还原之后：1767 个节点、388 个 TextControl、299 个中文节点、36 条消息。** 遍历耗时约 2 秒。

### 还有两个 Chromium 的坑

1. **a11y 树是懒建的**：直接 UIA 遍历只会看到一个光杆 Window 节点。得先用 MSAA 的
   `AccessibleObjectFromWindow` 捅一下，Chromium 才建树（治具实测：捅之前 ControlView 1 个
   节点，捅之后 56 个、RawView 131 个）。探针里那次 poke 不是可选项。
2. **Chromium 把 DOM 的 class 名暴露在 `ClassName` 上**。这比预期好得多——飞书的 class 名
   是语义化的，等于白送一份结构说明。`lark-mbti-jev` 那套压根用不上（见下）。

### 消息结构（实测形状）

```
js-message-item message-item message-not-self message-item-first message-me-read text-message
  Aid = 7690500277727661005            <- 消息 ID，19 位数字
  ├─ message-left   (宽 69)            <- 头像栏
  ├─ message-right  (宽 1318)          <- 内容栏
  │   ├─ message-info-name             <- 群聊里的发言人名
  │   ├─ NewMessageContextMenuTrigger  Aid=同一个消息 ID
  │   │   └─ message-content → limit-height-container
  │   │        └─ TextControl          <- 正文挂在它的 Name 上
  │   └─ message-section-right         <- 时间 / 已读状态
  └─ tips / reply-meta-tips
```

**`message-left` / `message-right` 不是收发方向**，是同一条消息里的头像栏和内容栏（差 11 个像素，
各 35 个）。差点照字面理解用错。

### 五个问题的答案

| # | 问题 | 结论 |
| --- | --- | --- |
| 1 | 正文在不在树里 | ✅ **在**。挂在 TextControl 的 `Name` 上，实测有整句中文（cjk=15/len=15） |
| 2 | 能不能分 me / her | ✅ 有现成标记 `message-self` / `message-not-self`。⚠ 但**只验到了 not-self 一侧**，见下 |
| 3 | `messenger-chat:` 容器 | ❌ **没有**——那是安卓版的写法。Windows 版要用 DOM class：`list_items` / `messageList-row-wrapper` / `js-message-item`。**别照抄 `lark-mbti-jev`** |
| 4 | 语音 / 图片消息 | ✅ 类型也在 class 上：`text-message`(31) / `im-image-message`(2) / `post-message`(2) / `system-text-background`(1)，另有 `message-comment`(8)、`message-has-reactions`(3)、`mention`（@提及，带自己的 Aid）。**语音的 class 还没看到**（当前会话没有语音） |
| 5 | 虚拟化列表 | ⚠ **滚出视野的消息仍然留在树里**——`list_items` 容器高 6126px，窗口可视区才 ~1100px，36 条消息的 y 从 -5090 一直到 +1300。**读的时候必须按视口过滤**，否则会把看不到的旧消息当新的 |

### 这条路比 OCR 好在哪

| | 现在的微信（截图 + OCR） | 飞书（UIA） |
| --- | --- | --- |
| 正文 | RapidOCR + 三道阈值（众数占比 0.45 / 墨高 0.6×lh / 对比度 150） | 直接读 `Name` |
| 收发方向 | 气泡底色众数分类（`who_said`），单字消息会判错 | class 上写着 `message-self` / `message-not-self` |
| 消息类型 | 靠正则 + 图标像素校验猜（`_VOICE` / `_has_icon` / `_VOICE_ICON`） | class 上写着 `text-message` / `im-image-message` / … |
| 去重 | 子进程 `Reader.seen` + 父进程 `_already_read()` 两道模糊匹配 | **消息 ID**（`Aid`，19 位数字），精确 |
| 代码量 | `capture.py` 197 行 + `ocr.py` 568 行 | 遍历 + 取字段 |

短消息被 OCR 整条吃掉（`CLAUDE.md` 里那个【未解决】）这类问题，在飞书这边不存在。

### 还没验的

1. **`message-self` 标记**——当前会话里用户没发过言，36 条全是 `message-not-self`。
   **需要在一个自己说过话的会话里再跑一遍**才能确认 self 侧的标记名。这是唯一挡着阶段 1 的。
2. **语音消息的 class 名**——当前会话没有语音。
3. 群聊的发言人区分（`message-info-name` 是不是稳定给名字）。
4. 窗口被遮挡 / 未聚焦时树还全不全（截图上 WGC 不受遮挡影响，UIA 大概率也不受，
   但得实测）。
5. 遍历耗时 2 秒——对「静默窗口到期读一次」够用，对「每帧」太慢。要不要增量读得看阶段 1。

> `lark-mbti-jev` 那个「正文走 lark-cli 还是 UIA」的疑问，现在有答案了：**UIA 就能拿到正文**，
> 它大概是拿 UIA 定位标签、又另外用 lark-cli 拉完整历史（README 的数据表说首次读近 90 天 1000 条，
> 那不是屏幕上能看到的量）。**我们不需要 lark-cli。**

## 这触碰了硬约束 2，要先拍板

`CLAUDE.md` 硬约束 2 写的是：

> 采集只用窗口级截图 + 本地离线 OCR。不 hook、不注入、不读微信数据库、不解密、不碰微信进程。

UIA 读控件树**仍然只读、仍然非侵入**（不 hook、不注入、不碰进程内存），但它确实**不是**
「截图 + 本地离线 OCR」。所以给飞书接 UIA，等于要改这条约束。

两条路，得先选一条：

1. **放宽硬约束 2**，写成「采集只用只读、非侵入的方式：微信走窗口级截图 + 本地离线 OCR，
   飞书走系统无障碍接口读控件树」，然后飞书走 UIA。
2. **不改约束**，飞书也走截图 + OCR——那 UIA 的便利全白瞎，还要把微信那套阈值
   （众数占比 0.45 / 墨高 0.6×lh / 对比度 150）在飞书上重调一遍。

顺带一条：硬约束 1 是「只读自己设备上、自己有权查看的对话」。**飞书多半是公司账号**，
聊天记录的归属跟个人微信不是一回事，接之前自己想清楚。

## 后续接入方案

### 阶段 0：可行性实测 —— ✅ 已完成

`probe/probe_feishu.py`，只读、不点击、不输入、不 Invoke、不出图、不落盘。

```bash
pip install uiautomation
python probe/probe_feishu.py --unminimize            # 全量节点 dump
python probe/probe_feishu.py --messages --unminimize # 只看消息列表（条数/收发标记/正文挂哪/虚拟化）
```

默认把每个节点的文字**遮成「长度 + 字符类型」只报结构**，正文要 `--raw` 才出来——
贴结论给别人看的时候别加 `--raw`。

结论：**UIA 这条路成立**，详见上面「实测结果」。剩下的是第 1 条（`message-self` 标记）
没验完，那是阶段 1 的前置。

### 阶段 1：UIA 可行 → 抽采集层

现在 `app/worker.py` 的采集是写死微信的（`capture` + `ocr`）。把采集抽成一层接口，
微信一路、飞书一路，**下游一个字不用改**：

- **队列协议不用动**——`lines` / `voice` / `chat` / `area` 那套照用，`main.drain()` 不用改
- 判断链 `core/` 本来就平台无关，直接复用
- 新模块 `app/feishu.py`（或 `app/uia.py`），**记得进 `jev.spec` 的 `hiddenimports`**
  ——worker 是 spawn 出来的子进程，静态分析扫不到，漏了就是打包后启动即炸

采这块要照实测结论来，别照 `lark-mbti-jev`：

- **进去先 poke**（`probe_feishu.poke_msaa`）：不捅一下 Chromium 不建树，只能看到 1 个节点
- **定位消息区用 DOM class**（`js-message-item` / `list_items`），不是 `messenger-chat:`
- **去重用消息 ID**（`Aid`，19 位数字）——比现在那两道模糊匹配靠得住得多
- **按视口过滤**：滚出视野的消息仍在树里（容器 6126px vs 可视区 ~1100px），
  不过滤就会把看不到的旧消息当新的
- **最小化时要先还原**（`--unminimize` 那套），否则一个字都读不到

**COM 坑**：`app/shortcut.py` 已经踩过一次——**COM 是按线程算的**，A 线程初始化、
B 线程调 `CoCreateInstance` 会拿到「尚未调用 CoInitialize」（0x800401F0）。
那边 `_ensure_com()` 是在每个入口自己保证的，UIA reader 在 worker 子进程的线程里也得照做。

### 阶段 2：填入

`app/fill.py` 现在是按微信布局算输入框坐标的——`fill()` 拿 `rect` 的
`(x0, _, _, y1)`，底线下方 40px、左边界右侧 60px。**飞书窗口布局不同，这套坐标不能直接用。**

两个选择：另算一套坐标，或者走 UIA 直接往输入控件写（`lark-mbti-jev` 没做这件事，得自己试）。

**不管走哪条，`press_enter()` 那条边界不变**：全工程只有 `auto_send` 那个默认关着的口子会发送，
加飞书**不许新增第二个调用点**。

### 阶段 3：UIA 不行 → 退官方 API

就是 `Hatuw/jev-chat-feishu` 那个形态：企业自建应用 + 消息快捷操作 + 侧边栏网页应用，
需要**管理员审批**，个人用不了。

而且那样采集就不是本机读屏了，是走网络接口拿消息——硬约束 1 和 2 都得重写，
**基本等于另起一个项目**，跟本仓库共用不了多少东西。这是下策。

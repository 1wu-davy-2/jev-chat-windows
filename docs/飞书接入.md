# 飞书接入

2026-09-29 排查：飞书有没有现成的 jev-chat、要不要给本项目加飞书、怎么加。

## 一句话结论

**Windows 版 jev-chat 目前一个都不支持飞书**（上游 143 个 fork、issue/PR 里 0 条提过飞书）。

但排查里有个反直觉的发现，直接决定后面怎么做：**飞书桌面端不用 OCR**——它的控件树里有正文，
跟微信正好相反。微信那条路之所以是本仓库现在这样（截图 + 一整套阈值），是因为微信界面自绘在
GPU 画布上、控件树是空的（见 `KICKOFF.md`「为什么走 OCR」）。**飞书没这个问题。**

## 关键发现：飞书桌面端的控件树里有正文

`iikawa-games/lark-mbti-jev` 的 `feishu_mbti/accessibility.py`，头一行 docstring：

> Read Feishu's desktop text and coordinates through Windows MSAA.
> **No screenshots, OCR, selection changes or client injection are used here.**

具体读法（同一个文件）：

- `chat()` —— 广度优先遍历控件树，找 `accName` 里含 **`messenger-chat:`** 的节点，拿它的
  `accLocation` 当消息区矩形。遍历上限 240 个节点 / 0.75 秒。
- `text()` —— 从 `obj.accName[child_id]` 取文字，`accRole` 在 **40–43**（文本角色）才算，
  单条长度 ≤ 2000 字符。上限 4000 节点 / 2 秒，**读不完就整份丢掉**（不要半份）。
- 技术栈：`comtypes` 调 `oleacc.dll` 的 `AccessibleObjectFromWindow` / `AccessibleChildren`，
  纯 stdlib + comtypes，没有额外依赖。

它顺带处理掉的两件事，本仓库现在是花力气自己做的：

| | 本仓库（微信） | `lark-mbti-jev`（飞书） |
| --- | --- | --- |
| 定位消息区 | `capture.chat_area()` 认底色和细横线，纯像素锚点 | 找 `messenger-chat:` 容器，直接给矩形 |
| 虚拟化列表 | 不需要考虑 | 有专门处理：内容比容器高 = 滚动列表；**滚出视野的消息可能仍留在虚拟树里**，按 `clip` 过滤 |

### 一个没验证清楚的地方

`lark-mbti-jev` 的 README 数据表写着「群聊消息：**通过 lark-cli 读取所选群**」，而
`accessibility.py` 的 `text()` 又是从 `accName` 取正文的——两处对不上。

可能是 UIA 只用来拿**姓名和位置**（给标签定位用），正文另有来源；也可能两条路都在用。
**这条必须实测才能定**，因为它决定飞书到底是「纯读屏」还是「得配官方 CLI」。

## 这触碰了硬约束 2，要先拍板

`CLAUDE.md` 硬约束 2 写的是：

> 采集只用窗口级截图 + 本地离线 OCR。不 hook、不注入、不读微信数据库、不解密、不碰微信进程。

UIA 读控件树**仍然只读、仍然非侵入**（不 hook、不注入、不碰进程内存），但它确实**不是**
「截图 + 本地离线 OCR」。所以给飞书接 UIA，等于要改这条约束。

两条路，得先选一条：

1. **放宽硬约束 2**，写成「采集只用只读、非侵入的方式：微信走窗口级截图 + 本地离线 OCR，
   飞书走系统无障碍接口读控件树」，然后飞书走 UIA。
2. **不改约束**，飞书也走截图 + OCR——那 UIA 的便利全白瞎，还要把微信那套阈值
   （众数占比 0.45 / 墨高 0.6×lh / 对比度 150）在飞书上重调一遍。

顺带一条：硬约束 1 是「只读自己设备上、自己有权查看的对话」。**飞书多半是公司账号**，
聊天记录的归属跟个人微信不是一回事，接之前自己想清楚。

## 后续接入方案

### 阶段 0：可行性实测（先做这个，不写生产代码）

加 `probe/probe_feishu.py`，性质跟 `probe/probe_win.py` 一样——一次性探针，结论写进本文档。

技术路线照抄 `lark-mbti-jev` 的 `accessibility.py`（`comtypes` + `oleacc.dll`）。
dump 出每个节点的 `accName` / `accRole` / `accLocation`，按 y 排序打印。

要回答的五个问题：

1. **正文在不在 `accName` 里**——role 40–43 的节点是不是消息正文，还是只有姓名/时间戳
2. **能不能分出 me / her**——微信靠气泡底色众数（`ocr.who_said`），飞书靠什么？
   （安卓版飞书是靠**已读状态**判的）
3. **`messenger-chat:` 容器稳不稳**——是不是消息区、单聊群聊都在、窗口大小变了还在不在
4. **语音 / 图片消息长什么样**——UIA 可能直接给节点类型，那本仓库那套语音正则 + 图标像素校验
   （`_VOICE` / `_has_icon` / `_VOICE_ICON`）就都不用要了
5. **虚拟化列表滚出去的消息还在不在树里**——在的话去重逻辑要重写

产出：一份文字 dump。据此决定阶段 1 还是阶段 3。

### 阶段 1：UIA 可行 → 抽采集层

现在 `app/worker.py` 的采集是写死微信的（`capture` + `ocr`）。把采集抽成一层接口，
微信一路、飞书一路，**下游一个字不用改**：

- **队列协议不用动**——`lines` / `voice` / `chat` / `area` 那套照用，`main.drain()` 不用改
- 判断链 `core/` 本来就平台无关，直接复用
- 新模块 `app/feishu.py`（或 `app/uia.py`），**记得进 `jev.spec` 的 `hiddenimports`**
  ——worker 是 spawn 出来的子进程，静态分析扫不到，漏了就是打包后启动即炸

**COM 坑**：`app/shortcut.py` 已经踩过一次——**COM 是按线程算的**，A 线程初始化、
B 线程调 `CoCreateInstance` 会拿到「尚未调用 CoInitialize」（0x800401F0）。
那边 `_ensure_com()` 是在每个入口自己保证的，UIA reader 在 worker 子进程的线程里也得照做。

### 阶段 2：填入

`app/fill.py` 现在是按微信布局算输入框坐标的——`fill()` 拿 `rect` 的
`(x0, _, _, y1)`，底线下方 40px、左边界右侧 60px。**飞书窗口布局不同，这套坐标不能直接用。**

两个选择：另算一套坐标，或者走 UIA 直接往输入控件写（`lark-mbti-jev` 没做这件事，得自己试）。

**不管走哪条，`press_enter()` 那条边界不变**：全工程只有 `auto_send` 那个默认关着的口子会发送，
加飞书**不许新增第二个调用点**。

### 阶段 3：UIA 不行 → 退官方 API

就是 `Hatuw/jev-chat-feishu` 那个形态：企业自建应用 + 消息快捷操作 + 侧边栏网页应用，
需要**管理员审批**，个人用不了。

而且那样采集就不是本机读屏了，是走网络接口拿消息——硬约束 1 和 2 都得重写，
**基本等于另起一个项目**，跟本仓库共用不了多少东西。这是下策。

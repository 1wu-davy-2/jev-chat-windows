| 任务 | 平台 | 现状 | 可行性 | 体量 |

## 二、飞书（Windows）

### 依据：已实测，不是推测

2026-09-29 用 `probe/probe_feishu.py` 在本机真机上验过：飞书开着聊天窗口时，UIA 读出
**1767 个节点、388 个 TextControl、36 条消息**，正文、收发方向（`message-self` /
`message-not-self`）、消息类型（`text-message` / `im-image-message` / …）**全都在树里**，
而且每条消息带一个 19 位的**消息 ID**（`Aid`）可以直接拿去去重。

`capture.py`（197 行）和 `ocr.py`（568 行）**整个不用带过去**——那 568 行里有大半是在跟
「短消息被吃掉」「气泡底色分谁说的」「语音正则 + 图标像素校验」这些微信特有的问题打架，
飞书这边 class 名直接写着答案。

细节和坑（最小化读不到、Chromium a11y 树要先 poke、消息区要按视口过滤）见
[飞书接入.md](飞书接入.md)「实测结果」。

### 要写什么

| 阶段 | 内容 | 落点 |
| --- | --- | --- |
| 0 探针 | ~~遍历控件树，把五个问题测掉~~ **✅ 2026-09-29 已完成** | `probe/probe_feishu.py` |
| 1 采集 | 新采集器，吐跟现在**完全一样**的队列消息 | `app/feishu.py` + `worker.py` 抽一层接口 |
| 2 填入 | 输入框定位 / 写入 | `app/fill.py` 另算一套，或走 UIA |

**下游一个字不用改**：队列协议（`lines` / `voice` / `chat` / `area`）、`main.drain()`、
`core/` 整条判断链、`overlay.py` 全部照用。这是当初「两个进程 + 两条队列」分层分对了的地方。

工作量大头从「能不能读」变成了**「怎么把它接成现在这套队列」**——读的部分已经没悬念了。

### 风险

- **硬约束 2 要改**（见第七节）——这是**唯一的阻塞项**，而且不是技术问题。
- **`message-self` 标记还没验到**——探针跑的那个会话里用户没发过言，36 条全是
  `message-not-self`。**这是阶段 1 开工前唯一的硬前置。**
- **遍历一次约 2 秒**（1767 节点）。对「静默窗口到期读一次」够用，对「每帧」太慢——
  所以不能照搬现在 worker 那个「每帧 OCR」的循环，得改成定时/触发式。
- 语音消息的 class 名还没见到（当前会话没有语音），阶段 1 前补一条验一下。
- COM 按线程算（`app/shortcut.py` 踩过），worker 子进程里要自己保证。

## 三、抖音聊天（Windows）

### 现状：一无所知，得先探

- **没有任何 jev-chat 做过抖音。** `1104480426-hash/jev-wingman` 支持抖音，但那是**安卓**版、靠无障碍，跟 Windows 无关。
- **本机没装抖音**，没法当场验。
- **技术栈未知**——这是最大的未知数。抖音 PC 客户端如果是 Electron/CEF，Chromium 的无障碍树有机会（但 Chromium 默认不暴露，得看它开没开）；如果是自绘，就只剩截图 + OCR，等于把微信那套再调一遍。

### 两条路

| 路 | 怎么做 | 跟硬约束的关系 |
| --- | --- | --- |
| **A. PC 客户端读屏** | 跟微信/飞书同构：找窗口 → 读消息区 → 分 me/her | **符合**（还是只读自己的屏幕） |
| **B. 网页版** | 驱动 douyin.com 的私信页 | **违反硬约束 2**——那不是「读自己屏幕上的窗口」，是驱动网页；而且抖音风控比微信严得多 |

参考：`Aaron-gx/douyin-fire-desktop` 走的是 B 那条（Electron 内嵌抖音聊天页 + 持久登录）。
**它能跑通不等于 A 走不通**，只是说明 B 有人试过。

### 先做什么

**装一个抖音 PC 客户端，拿现成的 `probe/probe_feishu.py` 改个进程名跑一遍。**
飞书的探针已经写好了，它是通用的（找窗口 → poke → 遍历 → 统计 class），抖音要改的只有：

- `FEISHU_EXES` 换成抖音的进程名
- 如果抖音 PC 客户端**也是 Electron**（窗口类 `Chrome_WidgetWin_1`、进程里有 msedgewebview2），
  那 poke 和 DOM class 那套大概率直接能用，只是 class 名不同（不会叫 `js-message-item`）
- 如果是自绘窗口（像微信），那 UIA 就是死的，直接退路线 B 或截图 + OCR

**先看窗口类名和进程树就能判断走哪条**，不一定要写完整探针。

探针要回答的跟飞书那五个问题一样，额外加一条：**抖音 PC 客户端到底是什么技术栈**
（看进程里有没有 `msedgewebview2` / 窗口类名是不是 `Chrome_WidgetWin_*`）。

### 风险

- **风控**：抖音对自动化的敏感度明显高于微信。只读（截图 / UIA）风险低，
  但这项目在「填入」那一步会**模拟粘贴**（`fill.py`）——那一步比在微信上更容易踩线，得单独评估。
- **技术栈黑盒**：如果客户端是自绘且更新频繁，OCR 那套阈值要跟着追，维护成本比微信高
  （微信至少本仓库已经调完了）。

## 四、安卓自定义中转

### 好消息：原版已经有一半

`jev-chat/jev-chat-jarvis` 的 `core/Prefs.kt` 里已经有：

| 已有的 | 位置 |
| --- | --- |
| 判断 / 回复 / 视觉**三路分别可填**地址、密钥、模型 | `SettingsActivity.kt` 三张卡 |
| **`PROVIDER_CUSTOM` 预设**——用户自己填完整 URL | `Prefs.kt:232` `PROVIDER_CUSTOM -> judgeBaseUrl.trim()` |
| 回复接口任意 OpenAI 兼容端点 | `Prefs.kt:238` `"{base}/chat/completions"` |
| 每张卡一键连通测试 | `SettingsActivity.kt` |

所以**不是「从零加自定义中转」**，是「补齐 Windows 那边已经有的三个能力」。

### 缺的三样（对着 Windows `core/relay.py` ）

| # | 缺什么 | Windows 怎么做的 | 不补会怎样 |
| --- | --- | --- | --- |
| 1 | **地址归一** | `relay.root()` 把 `/v1`、`/chat/completions` 尾巴去掉再拼 | 安卓直接拼 `/chat/completions`。用户从中转商拿到 `https://xxx/v1` 或完整 URL 就会拼成 `.../v1/chat/completions/chat/completions`，报 404 |
| 2 | **思考开关** | `THINKING_STYLES` 三派：DeepSeek 式 `thinking.type` / OpenRouter 式 `reasoning.enabled` / 不传 | **最实际的坑**：传错派系**不报错、只被无视**，思考照开、`max_tokens` 被推理吃光 → 起草回来空 content → 报「解析不出候选」 |
| 3 | **判断接口的中转** | base + 可配路径（`relay_judge_path`），因为各家判断口叫法不同（OpenRouter 是 `/api/alpha/decisions`，PackyCode 是 `/v1/systemone`） | 安卓现在自定义模式下要用户**自己填带路径的完整 URL**——能用，但不说人话 |

### 要写什么

- `core/Prefs.kt` 加字段（跟 Windows `settings.py` 那个 `save()` 整份重写的坑不同，安卓这边是 `SharedPreferences`，加键简单）
- `SettingsActivity.kt` 加控件（地址归一和思考开关各一个，跟前三张卡一行）
- `JudgeClient.kt` / `ReplyClient.kt` 拼 URL 的地方换成归一后的
- **思考开关**的字段塞进请求体（`HttpJson` 那条路）

体量：**小**。比飞书和抖音都小一个量级，而且**风险最低**（不碰采集，不碰系统接口，
纯配置 + 请求体拼装）。适合当「等飞书探针结果」那段空档里顺手做掉的活。

## 五、共同的底座

三件事共用的东西不一样，别指望一次抽象全包：

| 底座 | 飞书 | 抖音 | 安卓中转 |
| --- | --- | --- | --- |
| 判断链 `core/` | ✅ 直接用 | ✅ 直接用 | ✅ 原版自带 |
| 队列协议 + `main.py` | ✅ 协议不变 | ✅ 协议不变 | — |
| `oleacc` 探针 / 采集器 | 先写 | **复用飞书的** | — |
| `core/relay.py` 那套 | — | — | **搬过去** |

**值得单独抽的只有「采集器接口」这一层**：飞书和抖音（如果走 A 路）都是「UIA 读屏」，
微信是「截图 + OCR」，三者吐同一种队列消息。这层抽象做完，加第四个聊天软件的成本就只剩写适配器。

## 六、顺序建议

1. **补验飞书的 `message-self`**——最小的一步（在自己发过言的会话里跑一遍
   `--messages`），但它是阶段 1 的硬前置，不验完 Phase 1 没法开工
2. **安卓中转**——最小、最独立、零风险，可以立刻做掉
3. **飞书阶段 1/2**——读的部分已经通了，剩下的是接进队列 + 填入
4. **抖音**——先装客户端看窗口类名，判断走 A 还是 B，再排期

## 七、需要拍板的

1. **硬约束 2 改不改**（`CLAUDE.md`）——现在写的是「采集只用窗口级截图 + 本地离线 OCR」。
   飞书走 UIA 要改这条；抖音如果走 B 路（网页版）改得更多。**这是飞书能不能开工的前提。**
2. **抖音走 A 还是 B**——A 符合现有边界但技术栈未知；B 已知可行但违反边界 + 风控严。
3. **仓库/组织结构**——四个项目（windows / feishu / douyin / jarvis）怎么放，见下一节。
